# 2026-08-30 — Jaeger para tracing distribuido del sistema de agentes

Parte de la Idea 7 (post-roadmap): tracing distribuido sobre las llamadas del sistema multi-agente. Ver `devops-multiagent/docs/29110/idea7-tracing/` para el detalle completo. Esta entrada es solo el lado de infraestructura.

## Cambio
`docker-compose.yml`: nuevo servicio `jaeger` (backend de traces, recolector OTLP + UI), en el mismo LXC `observability` que ya corre Prometheus/Grafana/Alertmanager.

## Incidente: la imagen que se planeaba usar está EOL

`jaegertracing/all-in-one:1.65.0` arrancó, pero el log mostró de entrada: "End-of-life Notice for Jaeger v1 ... reach end-of-life on December 31st, 2025" — ya vencido a la fecha de esta entrada. Además falló de entrada por un error de permisos escribiendo en el volumen (`mkdir /badger/key: permission denied`), un problema aparte del EOL.

En vez de parchear v1 (arreglar el permiso y seguir con algo deprecado), se migró a **Jaeger v2** (`jaegertracing/jaeger:2.20.0`, imagen renombrada de `all-in-one` a `jaeger`) — mismo criterio ya aplicado en el proyecto con Node 20 y `podman generate systemd`: no usar algo deprecado solo porque "todavía funciona".

## Decisión: storage en memoria, no persistente

v2 cambió el modelo de configuración de storage: v1 usaba env vars simples (`SPAN_STORAGE_TYPE=badger`); v2 requiere un `config.yaml` propio de pipeline estilo OpenTelemetry Collector (extension `jaeger_storage`). Se decidió no pagar ese salto de complejidad para datos de traces — de naturaleza más efímera y reproducible que las métricas o los secretos (una traza vieja no tiene el mismo valor operativo que una métrica histórica o un secreto). Documentado como límite aceptado.
